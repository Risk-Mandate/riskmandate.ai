## In one paragraph

On the call we agreed the deployment: Claude in the browser, the Gmail connector on one mailbox, nothing else connected. What the deployer showed us the same day was reading the inbox and, with the approval prompt, sending one message. So the draft says: read is wanted; sending is wanted only while the prompt stays on; nothing that outlives a chat, and nothing that reads credentials on purpose. Every line below is a question for the customer before it is a mandate.

## What is wanted (2)

| Capability | What it is | Reach |
| --- | --- | --- |
| `read.message.tenant` | Read mail or chat it is connected to | tenant — the Google account the consent was given for |
| `send.message.world` | Send a message to anyone | world — anyone Claude replies to or forwards a message to |

## What is explicitly not wanted (2)

| Capability | What it is | Reach |
| --- | --- | --- |
| `read.credential.host` | Read credentials stored where it runs | host — the mailbox itself: every message and thread, labels, filters and saved drafts, and attachment metadata — never attachment content |
| `create.schedule.tenant` | Create something that outlives the session, on the platform (a routine, a scheduled trigger, a new session) | tenant — the Google account the consent was given for |

## Correct it

Move any capability between the three lists in `data/mandate.json` and rebuild. Three questions settle most rows:

- **Did you ask for this?** Then it is a want.
- **Would you object if it happened?** Then it is a do-not-want — and the barrier column in `GRANT.md` says whether anything actually stops it.
- **Neither?** Leave it unstated. Unstated rows in the grant are the ones that turn up in an incident report as "nobody said it couldn't".
