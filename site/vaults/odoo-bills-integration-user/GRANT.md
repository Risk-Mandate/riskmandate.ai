## What the words mean here

An agent holding the API key of an internal integration user on a self-hosted Odoo 20 Community database, for one job: turn incoming supplier documents into draft vendor bills. The user is not an administrator and is not in Accounting / Invoicing. It holds Odoo's default internal-user role and one group made for the job, whose access rows allow create, read and update on draft vendor bills and their lines, read on contacts, journals, accounts, taxes, currencies and payment terms, and delete on nothing. Measured on 16 November 2026 on an instance stood up for the exercise and torn down the same day: a static read of the user's access through Odoo's own checks (172 models with some access: read on 154, create on 56, update on 56, delete on 33), and 25 calls made with the key over Odoo's JSON-2 API, each recorded. The two rows on bills come from the job's group; supplier bank accounts, chatter email, scheduled messages, attachments and email templates come from the internal-user role every internal user holds. In the exercise the agent itself never held this key: it wrote proposed bills to a file, a person approved them, and a small broker applied them with the key. This vault describes the key, which is what an agent holding it can do.

| Reach | In this shape means |
| --- | --- |
| project | the draft vendor bills the key was given to create: account.move records of type in_invoice or in_refund, in state draft |
| host | the Odoo database as this user sees it: contacts, supplier bank accounts, journals and every other model the internal-user role reads |
| tenant | the Odoo database as an account the key acts in, and the company's mail sent through it |
| world | suppliers and anyone else outside the company, reached by email from a record's chatter |

## The notes behind the rows

- **`authenticate-as.credential.tenant`** — every call ran as bills-agent-integration, an internal user in one company; context_get returned its own user id, never the administrator's. The key was generated by the administrator for one day and deleted from the measuring environment at teardown. Odoo states that JSON-2 calls "are validated against the access rights, record rules and field accesses of the user" (https://www.odoo.com/documentation/20.0/developer/reference/external_api.html, read 2026-11-19), which is what makes this user's access the grant.
- **`read.file.host`** — Odoo's own access check reports read on 154 models. Read in the session: 41 contacts, and 6 supplier bank accounts (res.partner.bank, read granted to every internal user by the internal-user role, not by the job's group). Refused: posted bills, bank transactions (account.bank.statement.line), system parameters (ir.config_parameter), other users' API keys (it sees only its own key's name, never the secret).
- **`send.message.world`** — the call returned a message id and Odoo queued an email titled "Draft Bill (INV-WC-2291)" to the supplier's address. The instance had no outgoing mail server, so the email stayed in the queue marked exception and was never delivered; on a database with mail configured nothing in this user's access would stop it. Creating outgoing mail directly (mail.mail) was refused: the door is the chatter, not the mail queue.
- **`write.file.project`** — created draft vendor bills (two from supplier documents, totals matching the documents to the cent, and one probe bill, removed); edited a draft bill's reference after it had been approved, then restored it. Odoo would not create a bill with lines for a user who could only create: it refused with "You are not allowed to modify 'Journal Item'", so update cannot be withheld from a user that creates bills, and editing after approval comes with it. Refused: a customer invoice (out_invoice), any change to a posted bill, deleting a draft bill. Posting is in the blocked list.
- **`write.file.host`** — created an attachment (removed afterwards) and attached each supplier document to its bill. Odoo's own access check reports create on email templates (limited to templates the user created or owns) and update on the user's own contact; editing any other contact, including a supplier, was refused. All three come from the internal-user role.
- **`read.file.project`** — reads draft vendor bills and their lines, including the ones it created, which is how the totals were checked. Reading a posted bill was refused: the access row's domain limits the user to draft vendor bills, so the archive of posted bills is outside this grant.
- **`create.schedule.tenant`** — Odoo's own access check reports create on scheduled messages, on records the user can reach and limited to its own, from the internal-user role: a message that sends later, after the agent's session has ended. Read from the access check on the measured instance, not exercised. Creating a scheduled action (ir.cron) and a server action were both refused.

## The four barriers, and the test

| | Barrier | What stands in the way | Is it a control |
| --- | --- | --- | --- |
| ● | none | nothing in the way | no |
| ◉ | expectation | a rule in prose, enforced by nobody | no |
| ◐ | setting | a switch the agent's own account can flip | no |
| ○ | boundary | enforced above the grant, out of the agent's reach | **yes** |

> A control bounds a grant only if it is enforced by something the grant does not include.

A setting the agent's own account can change is not a control, because the grant includes the ability to remove the bound. A boundary enforced above it is one, because it does not.
